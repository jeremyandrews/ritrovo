# Ritrovo: Forms and User Input

Every form a person can type into on this site, where it comes from, and what it
can and cannot do on the kernel Ritrovo pins.

This is tutorial material and a record of what was verified. Each claim below is
covered by a test named at the end of its section, and those tests drive the real
kernel over a real Postgres rather than a model of it. Where the kernel cannot do
something the brief asks for, the section says so and names the `FRICTION.md`
entry rather than pretending.

**Kernel:** Trovato `v0.102.0`, rev `20baa121810b5c656b3f80028335770069fab5e0`.

---

## The one thing to understand first

Trovato has a Form API. `FormService` builds a form from a definition, validates
it, submits it, and dispatches `tap_form_alter`, `tap_form_validate`,
`tap_form_submit` and `tap_form_ajax` on the way through.

**No route calls it.** That is the kernel's own assessment, written in
`crates/kernel/src/routes/plugin_api.rs`:

> The form taps were unreachable: `FormService` is constructed and exposed on
> `AppState`, and no route calls `build` or `process`.

So the four form taps are declared, dispatched by a service, and the service is
dead code. A plugin cannot add a field to a form, reorder one, inject a button,
or validate one. `FRICTION.md`, `G-FORM-TAPS-UNREACHABLE`.

Everything below follows from that. There are exactly two kinds of form on this
site, and the difference between them is the difference between what the kernel
generates and what Ritrovo serves:

| | Generated by the kernel | Served by Ritrovo |
| :- | :- | :- |
| Example | the conference edit form | the member profile |
| Built from | the item type definition | plugin code |
| Ritrovo's part | configuration only | `tap_api` + `tap_menu` |
| Can a plugin change it? | no | it is the plugin |
| Rich text | yes, administrators only | no |

## 1. The conference edit form

**This form is configuration. Ritrovo writes no code for it at all.**

An editor opens `/item/{id}/edit` and gets a form with a widget for every field
`demo/config/item_type.conference.yml` declares. Nobody wrote those widgets:
`FormBuilder` walks the type definition and renders one per `FieldType`. Adding a
field to the conference type adds it to this form, and removing it removes it.

That is the whole of story 36.1's "auto-generated from the Item Type definition",
and it is why the right answer here was to configure rather than to build.

### Try it

```
# as editor_alice (the demo's editor account — see docs/EDITORIAL.md)
open http://127.0.0.1:3000/conferences
# follow any conference, then /item/<its id>/edit
```

You get a text input for `field_city`, a date input for `field_start_date`, a
checkbox for `field_online`, an autocomplete box for `field_speakers`, a file
input for `field_logo`, and a CSRF token in a hidden `_csrf` field. The form
posts `application/x-www-form-urlencoded` to its own URL and works with
JavaScript switched off.

### What it cannot do, and what that costs

Three of the brief's fields do not survive this form, and it is worth being
precise about why, because they fail for three different reasons.

**`field_topics` is not on the form at all.** The brief wants a multi-value
category reference. The kernel's `FieldType` has twelve variants and none of them
is taxonomic, so the field cannot be declared
(`G-NO-CATEGORY-REFERENCE-FIELD-KIND`). It is deliberately left undeclared: as
`Text` it would render a one-line box over a JSON array, which is worse than
being invisible. The value is still written, read and queried — the topic
gathers match on it — it simply has no widget.

**`field_speakers` and `field_venue_photos` render one widget each, over an
array.** Both declare `cardinality: -1`, which is what the brief means and what
the config format records, and **nothing in the kernel reads it**: no form
renders a second widget, no submit handler collects one, nothing validates a
count (`G-CARDINALITY-IS-INERT`). The brief's "Add another speaker" is not
buildable here, and is not attempted.

**And then saving destroys all three.** This is the part that matters most and
is easiest to miss. `ItemSubmission::from_form` builds a **fresh** field map out
of the POST body, and `Item::update` writes it whole:

```rust
let fields = input.fields.unwrap_or(current.fields);   // models/item.rs
```

A field the form could not render was not posted, so it is not in the map, so it
is gone from the item. Not left alone: gone. `G-FORM-SAVE-DROPS-EVERY-FIELD-THE-FORM-DID-NOT-RENDER`.

So an editor who corrects a typo in a conference's city, through the form the
kernel gives them, silently deletes its topics, its speakers and its venue
photos. That is recorded rather than worked around: a hidden input carrying the
JSON back would be a plugin taking responsibility for a kernel invariant, and the
first time the two disagreed the data would be worse off than it is now.

**Every value it does store is a string.** The date and the boolean go in typed
and come back as text, because the front-end form runs none of the admin form's
typed processing (`G-FRONTEND-ITEM-FORM-STORES-EVERY-FIELD-AS-A-STRING`).

### Rich text: the kernel has it and an editor cannot reach it

`field_description` is a `Blocks` field, which is the kernel's rich text: the
block editor edits it, and `render_blocks` sanitizes its output through ammonia
on the way to the page, which is what the brief's `filtered_html` asks for.

`FormBuilder` renders the container the editor attaches to, `<div
data-block-editor>`, on this form. Nothing ever attaches to it, because
`/item/{id}/edit` builds a bare HTML document with a `<style>` block and **no
`<script>` of any kind**. It is not the site template and it loads no assets.

The editor works on the administrator's content form, which does load it — and
which editors cannot reach, because the admin screens require the administrator
flag whatever a role grants (`G-ADMIN-SCREENS-ARE-ADMIN-ONLY`). So on this
kernel rich text is administrator-only in practice. New finding:
`G-ITEM-EDIT-FORM-LOADS-NO-ASSETS`.

### Verified by

`plugins/ritrovo_access/tests/ritrovo_access_host.rs`:

- `the_conference_edit_form_is_generated_from_the_type_and_has_no_editor` — an
  editor gets 200, every declared field has a widget, `field_topics` has none,
  and the page carries no script.
- `saving_the_edit_form_keeps_rendered_fields_and_drops_the_rest` — posts the
  form as a browser would and asserts what survived and what did not.

Those tests are written so that **if the kernel is fixed they fail**, naming the
`FRICTION.md` entry to reopen. A test that pins a loss has to break when the loss
stops happening, or it becomes the reason nobody notices.

## 2. The member profile

**This form is code, and it is Ritrovo's**, in the `ritrovo_forms` plugin.

### Why it is not on `/user/profile`

The kernel has a profile form. It carries a username, an email address, a
timezone and a password change, and it is not extensible by any means: the POST
handler extracts a fixed `Form<ProfileFormRequest>`, so an extra input posted to
it is discarded by serde before any code runs, and no tap is dispatched anywhere
along the route. There is no seam. `G-USER-PROFILE-NOT-EXTENSIBLE`.

So Ritrovo serves its own page, at `/user/bio`, holding the fields the kernel's
page does not. Two pages rather than one is the honest shape of what this kernel
allows, and each links the other.

### How a plugin serves a form at all

This is the interesting part, and it is new: before `KERNEL_API_VERSION (0,101)`
a plugin could not serve a working form, and `plugins/trovato_contact` in the
kernel is the worked example that exists because those seams were added for it.

Three things have to be true, and now are:

1. **A route the plugin owns.** `tap_menu` registers a `MenuRoute::api` with a
   method, a path and a callback; the kernel builds an axum route for it at
   startup and dispatches matching requests to `tap_api`.
2. **A token the form can carry.** A plain HTML `<form>` cannot set an
   `X-CSRF-Token` header. A plugin-served POST therefore also accepts a `_token`
   field in the body, and the kernel mints a token per request and hands it over
   in `ApiRequest::csrf_token` for the plugin to render into a hidden input.
3. **A page in the site's theme.** `ApiResponse::themed` asks for the response to
   be wrapped in the site's page template, so a plugin page is not a bare
   document.

The whole route registration is:

```rust
#[plugin_tap]
pub fn tap_menu() -> Vec<MenuRoute> {
    vec![
        MenuRoute::api("GET", "/user/bio", "profile_show")
            .permission("view own profile").parent("/user").visible(),
        MenuRoute::api("POST", "/user/bio", "profile_save")
            .permission("view own profile"),
    ]
}
```

Two entries for one path, one per method, so the form posts back to the URL it
was served from. Only the `GET` is visible in navigation: a menu link to a `POST`
is a link that cannot be followed.

**The permission is the gate and the kernel applies it**, before dispatch, so an
anonymous request never reaches the plugin. `view own profile` is a kernel
permission held by the `authenticated user` role, which is every signed-in
visitor and no anonymous one. It is not one of this plugin's own permissions,
because a plugin's permissions are declared into a void: `tap_perm` is never
dispatched, so no role can hold one (`G-PERM-TAP-NOT-DISPATCHED`).

### Try it

```
# sign in as any account, then
open http://127.0.0.1:3000/user/bio
```

Type a bio, save it, reload. Then turn JavaScript off and do it again: nothing
changes, because there is no JavaScript in it.

### What it cannot do

**No avatar.** A plugin cannot accept a file. There is no file host interface,
`tap_api` hands over a body string rather than a parsed multipart request, and
nothing a plugin can call stores an upload or promotes it out of temporary.
`G-FILE-NO-HOST-API`. The A7 work that renders an avatar beside a comment waits
on the same entry.

**No rich text.** The bio is plain text, rendered as escaped paragraphs. The
kernel's `filtered_html` is an ammonia pass the kernel runs and **no host
function exposes it to a plugin**. The two alternatives were to accept HTML and
render it, which is a stored-XSS hole because the kernel does not sanitize a
plugin's response body, or to ship a second sanitizer inside a WASM module. New
finding: `G-NO-TEXT-FORMAT-HOST-API`.

**No redirect after login.** An anonymous visitor gets `401`, not the login page:
a plugin route cannot set a response header, so nothing in this path can send a
`Location`. `G-PLUGIN-ROUTE-NO-HEADERS`.

### Where the bio lives

A plugin-owned table, `ritrovo_profile`, created by a migration the manifest
declares and the kernel runs. One row per user who has written something. No
foreign key to `users`: the kernel deletes a user by reattributing their content
rather than cascading, and a `REFERENCES` clause here would make a user deletion
fail on a table the kernel has never heard of.

### Verified by

`plugins/ritrovo_forms/tests/ritrovo_forms_host.rs`, nine tests over the real
router and a real Redis session, every POST sent as a browser sends one:

- the migration runs and creates the table;
- a member writes a bio, it lands in the table, and it comes back on the page;
- saving twice updates one row;
- a POST with no token is refused **by the kernel** and writes nothing;
- a replayed token is refused, because a token is single-use;
- an over-long bio is refused with a message, stores nothing, and the page it
  comes back on is still usable;
- HTML in a bio is escaped on the way out;
- an anonymous visitor is refused before the plugin runs.

## 3. CFP date validation

The rule is the brief's: **a call for papers cannot close after the conference it
is calling for has ended.**

It is implemented in `ritrovo_cfp` as `date_complaint`, a pure function over two
dates, and unit-tested at the boundary: closing on the final day is allowed,
closing the day after is not, a missing date is not the rule's business, and an
unparseable date is not reported as wrong.

**The kernel cannot enforce it.** `tap_item_presave` is dispatched and can modify
`fields`; the kernel then merges what comes back and saves unconditionally. There
is no return value that refuses a write, for create or for update, and no way to
put a message in front of the editor who typed the dates —
`tap_form_validate` is dispatched by the `FormService` no route calls.
`G-PRESAVE-CANNOT-REFUSE`, `G-FORM-TAPS-UNREACHABLE`.

So the tap reports and changes nothing. Clamping the CFP date to the end date was
the other candidate and is worse: both dates are individually usable, the plugin
cannot know which one was mistyped, and silently rewriting one turns a visible
contradiction into an invisible wrong answer.

**A rule can only be enforced where something is allowed to say no**, which on
this kernel means a form Ritrovo serves itself.

### Verified by

- `plugins/ritrovo_cfp/src/lib.rs` unit tests — the rule, at its boundaries.
- `the_kernel_saves_contradictory_cfp_dates_because_no_tap_can_refuse` in
  `plugins/ritrovo_cfp/tests/ritrovo_cfp_host.rs` — the gap, pinned. If the
  kernel grows a veto this test fails and STATUS 36.5 reopens.

## What is not here

Named so that their absence is a decision on the record rather than an oversight.

| The brief asks for | Why it is not here |
| :- | :- |
| `tap_form_alter` altering the edit form | `G-FORM-TAPS-UNREACHABLE` |
| Topic autocomplete against the category tree | `G-NO-CATEGORY-REFERENCE-FIELD-KIND` |
| "Add another speaker" | `G-CARDINALITY-IS-INERT`, `G-AJAX-ADMIN-ONLY-NO-CONDITIONAL-FIELDS` |
| Conditional CFP fields via AJAX | `G-AJAX-ADMIN-ONLY-NO-CONDITIONAL-FIELDS` |
| Avatar upload | `G-FILE-NO-HOST-API` |
| Bio with a WYSIWYG | `G-NO-TEXT-FORMAT-HOST-API` |
| A validation error shown on save | `G-PRESAVE-CANNOT-REFUSE` |
| Redirect to login for anonymous | `G-PLUGIN-ROUTE-NO-HEADERS` |
