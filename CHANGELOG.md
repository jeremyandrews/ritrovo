# Changelog

## Unreleased

- **The pinned kernel is Trovato 0.103.0, and four of this repository's kernel blockers closed with it.** `scripts/sync-kernel-release.sh --set-version 0.103.0` moved the pin and the twelve places that derive from it; the demo came up on the new image with every one of its own checks passing. Each constraint A7 depends on was re-derived against the new revision rather than carried forward, and `FRICTION.md` marks what changed **at the entry** rather than deleting it: `G-PERM-TAP-NOT-DISPATCHED`, `G-PERM-GRID-SAVE-REVOKES-PLUGIN-GRANTS`, `G-USER-API-NO-ADMIN-BYPASS` and `G-TRANSLATION-NO-WRITE-PATH` are fixed, `G-ADMIN-SCREENS-ARE-ADMIN-ONLY` is narrowed to the content list, and the mail, queue and item-write entries were re-confirmed as written.
- **Comments are open to every signed-in member, which was one line of configuration and a release of waiting.** The kernel's comment system has always worked and Ritrovo has never used it, because `post comments` belongs to a plugin and no role could hold a plugin's permission: `tap_perm` was declared in the WIT and dispatched nowhere. 0.103.0 dispatches it into a `plugin_permission` table that config import reads, so `demo/config` grants `post comments` and `edit own comments` to the authenticated role and the thread renders with the kernel's own depth classes. **No template was needed** — the kernel already renders the thread under an item, and the only thing standing between a member and it was the grant.
- **Comment moderation is the editor's, and that row was supposed to stay blocked.** The prompt for this work listed `/admin/content/comments` as out of scope because it required the administrator flag whatever a role granted. At 0.103.0 all six comment routes ask for `administer comments` instead, and `/admin` itself moved onto a new `access administration pages`. Granting both to the editor and publisher roles was the whole of story 37.2; no second moderation screen was built to get around anything. The content list and its bulk actions are still administrator-only, so the entry is narrowed rather than closed.
- **`ritrovo_notify` 1.2.0 is a real plugin again**, with three of its seven taps built and the other four naming what they wait on. `tap_perm` declares `manage own subscriptions`; `tap_menu` and `tap_api` serve `/user/{uid}/subscriptions` and its two writes as `_token` form posts with no JavaScript in them; `tap_queue_info` declares `ritrovo_notifications` as the JSON **array** the kernel reads, without the retry keys the kernel ignores — the object it used to return was ignored in full. Every menu entry's callback is served in the same change, asserted by a test rather than by reading, because a route that 404s is what this plugin was stripped for.
- **A subscription is stored in the kernel's own `user_subscriptions` table, not a private one.** The kernel created that table and has never called it. The database policy admits it: the allowlist is the union of the tables a plugin's migrations create and the tables its manifest names, checked by set membership, with no ownership concept and no denylist — two plugins in the kernel image already declare kernel tables this way. So the fallback of a private table and a migration was not needed, and a subscription the kernel's own model can read is what got written. The honest footnote is in the manifest: while `raw_sql = true` the table list is advisory, because the SDK wraps none of the four structured `db` calls the WIT declares.
- **Two permissions were asked for and one was declared.** `administer notifications` would gate a settings screen and a queue view, and neither exists, so declaring it would put a permission on the grid that an administrator could grant to no effect. It lands with the screen it is for. A unit test asserts the plugin declares exactly one.
- **The Subscribe toggle is not on the conference page, and that is a finding rather than an omission.** Two gaps close that door together and neither does alone: the item template's context carries no viewer, so a control rendered there would be shown to the anonymous visitors it would refuse (new: `G-ITEM-TEMPLATE-HAS-NO-VIEWER`), and `tap_item_view` — which *does* know the viewer — writes into `children`, the string that also carries the kernel's raw field dump and which this repository's conference template deliberately drops. Either fix opens it. Until then the control is on the plugin's own authenticated page, reached from the user menu, which the kernel filters per viewer, so no anonymous visitor is ever shown a control that will refuse them.
- **Three more `FRICTION.md` entries, all found by building the above.** `G-ITEM-TEMPLATE-HAS-NO-VIEWER`, above. `G-PLUGIN-PERMISSION-GRID-READS-BOOT-MEMORY`: enabling a plugin refreshes its declared permissions for `config import`, which reads the table, and not for the grid, which reads a boot-time in-memory registry — the kernel's own prose claims both in two places and its own test records the split. `G-QUEUE-WITHOUT-A-WORKER-IS-SILENT`: the drain skips a plugin with no `tap_queue_worker` with a bare `continue` and no log, so jobs accumulate forever without ever dead-lettering, which is why this plugin's queue declaration is free and also how a real fault would hide.
- **`scripts/demo-bootstrap.sh` enables `ritrovo_notify` and boots once before importing the config set.** Naming a plugin's permission in a role file makes the set depend on that plugin having declared it, and only a boot dispatches `tap_perm`. Found by running the demo from empty volumes, where the import failed on one line and wrote nothing. `ritrovo_notify` alone, because it has no `tap_install`; the other five cannot come early, since `ritrovo_importer`'s install needs the topics taxonomy that is in the set being imported. That is the circle, broken at its narrowest point.
- `tests/host/mod.rs`: serves the kernel's comment routes and layers its language middleware (inside the session layer, which is where it has to be); `register_declared_permissions` puts the plugin permissions `demo/config` grants into `plugin_permission` through the kernel's own parser and writer, because each test binary loads exactly one plugin and cannot ask the others what they declare.
- `scripts/verify-demo.sh`: the comment thread and the subscription flow against the released image — the login prompt an anonymous visitor gets, the form a member gets, a reply at `comment--depth-1`, the moderation queue open to editor_alice and shut to viewer_carol, a subscription landing in `user_subscriptions` and coming back out, another member's list refused, and `tap_perm`'s declaration reaching `plugin_permission`.

- **Submit a Conference: three steps, state on the server, no JavaScript.** `ritrovo_forms` 0.2.0 serves `/conferences/submit`, where a signed-in member describes a conference over three validated steps and confirms it onto the Incoming stage with themselves recorded as the author. The browser carries a draft id; the answers stay in a row keyed by that id **and** by `user_id`, so a hidden field cannot be edited into somebody else's submission and a step cannot be skipped — the row records how far it got, and the row is on the server. Seven host-in-the-loop tests and a step-by-step walkthrough in `verify-demo.sh` drive it the way a browser does: form-urlencoded, token in the body, no header.
- **The CFP rule is now enforced somewhere.** Step 2 refuses a call for papers that closes after the conference ends, with the message on the step that collected it. `ritrovo_cfp`'s presave tap can only report the same contradiction, because no tap can refuse a save. A rule can only be enforced where something is allowed to say no, and on this kernel that means a form Ritrovo serves itself.
- **Three more `FRICTION.md` entries, all found by building the above.** `G-NO-FORM-STATE-HOST-API`: the kernel has a form-state table, a writer for it and a cron task to expire it, and a plugin can reach none of them, so this plugin ships a second copy of all three. `G-PLUGIN-CANNOT-READ-BACK-AN-INSERT`: `query_raw` refuses anything that is not read-only and `execute_raw` returns a count, so a plugin generates its own keys — the WIT declares a structured `db.insert` that returns the row, and the SDK wraps none of the four structured calls. `G-BAD-CAPABILITY-NAME-MAKES-A-PLUGIN-VANISH`: one wrong word in `host_interfaces` reports the plugin as missing rather than as wrong, which cost a debugging cycle here.
- **A new plugin, `ritrovo_forms` 0.1.0, and a member profile that works.** The brief wants a profile with a bio; the kernel's `/user/profile` is a fixed struct with no tap anywhere along the route, so nothing can be added to it (`G-USER-PROFILE-NOT-EXTENSIBLE`). Ritrovo serves its own page at `/user/bio` instead, over a plugin-owned table, gated on a kernel permission the kernel checks before dispatch, and with no JavaScript in it. This is a **sixth plugin where the brief names five**, deliberately: none of the other five owns "the forms this site serves", and the kernel's own doctrine puts a feature in a plugin. Nine host-in-the-loop tests drive it through the real router and a real Redis session, posting the way a browser posts. The avatar half is not built and cannot be: a plugin cannot accept a file (`G-FILE-NO-HOST-API`), and the bio is plain text because no host function exposes the kernel's HTML filter to a plugin (new: `G-NO-TEXT-FORMAT-HOST-API`).
- **The conference edit form is configuration, and two tests now say exactly what it costs.** `/item/{id}/edit` already renders a widget for every field the conference type declares, so Ritrovo wrote no code for it. What was missing was evidence: a host-in-the-loop pair now drives it as a real editor and records that saving keeps every field the form rendered and **destroys `field_topics`, `field_speakers` and `field_venue_photos`** — the submission handler rebuilds the field map from the POST body and the update writes it whole. The tests are written to fail if the kernel is fixed, naming the entry to reopen, because a test that pins a loss has to break when the loss stops.
- **A correction to the 2026-09-17 audit.** It recorded WYSIWYG as "kernel has it, Ritrovo does not use it". `field_description` is a `Blocks` field and the kernel does render the block editor's container on the non-admin edit form — onto a bare HTML page that loads no scripts, so nothing attaches. Rich text is administrator-only in practice. New entry: `G-ITEM-EDIT-FORM-LOADS-NO-ASSETS`.
- `ritrovo_cfp` 1.2.0: the brief's CFP date rule, as `date_complaint` plus a `tap_item_presave` that applies it. It can only report — no tap can refuse a save and nothing can put a message on a form (`G-PRESAVE-CANNOT-REFUSE`) — and a host test pins that by saving a conference whose CFP closes after it ends. Clamping the date was rejected: both dates are usable, the plugin cannot know which was mistyped, and rewriting one turns a visible contradiction into an invisible wrong answer.
- `docs/FORMS.md`: every form on the site, where it comes from, what it cannot do and which `FRICTION.md` entry says why, with the test that verifies each claim.
- `tests/host/mod.rs`: serves the kernel's item routes, logs in as an ordinary member holding named demo roles rather than only as an administrator, posts form-urlencoded bodies the way a browser does, and clears Redis rate-limit counters between logins so a suite that signs several users in does not fail on the kernel's login limiter.

- `ritrovo_access` 1.2.0: `field_editor_notes` is hidden from non-editors by `tap_field_access`, which the kernel dispatches with the viewer and which removes the field from the Item before anything renders it. The `tap_item_view` stub it replaces is deleted; it fired on every item view and returned nothing, and a view tap could never have done this job because it can only append HTML. A host test asserts the key is absent from `Item.fields` for a reader and present for an editor, so this is access control rather than a template declining to print a value.
- `ritrovo_access` 1.2.0: the `tap_item_access` decision table is now a single unit test covering role, stage, operation and type together, and a host suite drives the four role-and-stage combinations that matter through roles resolved from the database the way a request resolves them. The previous host test built its own permission set, so it could not have noticed that no role can hold the permissions the brief names.
- **The editorial workflow now exists.** `ritrovo_importer` 1.3.0 lands imported conferences on Incoming instead of Live, and `ritrovo_access` 1.1.0 serves `/admin/content/editorial`, which moves a selection between Incoming, Curated and Live under a transition table that says who may make each move. The kernel cannot do this at all — no route, form, bulk action or host call changes an item's stage — so the plugin writes `stage_id` through the raw-SQL host call; `FRICTION.md` `G-NO-ITEM-STAGE-TRANSITION` records what that costs.
- `ritrovo_access` 1.1.0: creates the three editorial users (`editor_alice`, `publisher_bob`, `viewer_carol`) active and with roles in `tap_install`, and seeds an opening editorial state once enough of the import has arrived. The brief's route, registration plus SQL activation, cannot work: the kernel spends each rate limit twice per request, so three registrations per hour admits one (`G-RATE-LIMIT-COUNTED-TWICE`).
- `demo/config`: five role files (anonymous, authenticated, viewer, editor, publisher). They name only permissions the kernel itself defines, so the set imports into any Trovato database — naming another plugin's permission made it depend on that plugin's install order and broke the host-in-the-loop suites, which import into a bare database.
- `docs/EDITORIAL.md`: the workflow as four numbered walkthroughs, with the demo passwords, how permissions are really granted, and what revisions do instead of working.
- `scripts/verify-demo.sh`: asserts the editorial pipeline — each account logs in, the Incoming listing is 401/403/200 to visitor/reader/editor, a conference on Incoming is 404/404/200, Publish to Live is the publisher's alone, and the importer still lands on Incoming.
- `docker-compose.demo.yml`: `CACHE_TTL_ITEMS: 10`, because a plugin cannot invalidate the kernel's item cache, so a promoted conference 404s on its own page for up to five minutes on the default (`G-PLUGIN-CANNOT-INVALIDATE-THE-ITEM-CACHE`).
- The pinned Trovato release is authored once, in `kernel-release.toml`, and written into the eleven load-bearing places that repeat it by `scripts/sync-kernel-release.sh`; `--set-version X.Y.Z` resolves the tag against the public Trovato repository first. `demo/checks/tests/demo_wiring.rs` no longer carries a copy of the release and checks all eleven instead, including the six plugin manifests and both git `rev`s, which nothing checked before. Bumping the kernel is one command and a diff review.

- `ritrovo_cfp` 1.1.0: the CFP badge counted down from the item's last save (`changed`), not today; it now reads the database clock. Also parses the importer's `YYYY-MM-DD` deadlines, which previously showed no badge.
- `ritrovo_importer` 1.2.0: updating a conference wrote an empty `field_source_id`, so the next import could not find it and inserted a duplicate; the key is now written back, and migration 004 restores blanked keys and merges the duplicates.
- `scripts/verify-demo.sh`: the Italian check piped `curl` into `grep -q` under `pipefail`, so grep's early exit could SIGPIPE curl and fail a page that passed; it now matches the captured page.
- `ritrovo_notify` 1.1.0: removed the `/user/subscriptions` route that 404ed, the Subscribe button that did nothing, the queue nothing drained and the permissions nothing checked; its README describes the plugin still to be built.
